## ההחלטות שסוכמו

- כל סטודנט יוצר מאגר GitHub משלו. קובצי השירות שסיים ב-Part 2 יהיו בשורש המאגר, וה-workflow יהיה ב-`.github/workflows/ci.yml`.
- חשבונות GitHub והתחברות מוכנים לפני השיעור. יצירת המאגר עצמו היא חלק מהתרגול. כדאי לבדוק מראש גם Git מקומי ודרך רגילה לבצע push, כדי לא להפוך את שיעור ה-CI לשיעור authentication.
- כישלון מכוון באמצעות ציפיית health שגויה, 201 במקום 200, יודגם רק על ידי המרצה. אין משימת שבירה מכוונת לכל סטודנט בחלק הזה.
- זהו המשך Lab 1 המודרך: אותו API, אותו מודל, אותן חמש פונקציות בדיקה. אתגר עצמאי יגיע ב-Part 5; אין להוסיף או לפתור אותו כאן.

## מטרת ההוראה

להוביל את הסטודנטים מהפקודה המקומית `python -m pytest -q` להרצה חוזרת על GitHub אחרי push, ואז לבניית Docker image. הם צריכים לדעת לזהות כל שלב ולהראות את תוצאתו בלוגים.

לא צריך לשנן YAML. ה-starter מספק את המבנה, והסטודנטים משלימים ארבעה ערכים. אין צורך ב-matrix, caching, פרסום ל-registry, secrets מותאמים או deployment.

## בדיקות הכנה לפני השיעור

- קובצי ההתחלה נמצאים בתיקיית הסטודנטים, והפרויקט המושלם נמצא ב-`solutions/`. להכין עותק הדגמה נפרד ולוודא שגרסת Part 2 הסופית עוברת את חמש הבדיקות.
- לשמור את המודל הקיים ואת גרסאות Python/ML התואמות. `main.py` טוען את המודל בעת import, ולכן ה-checkout צריך לכלול `model.joblib` לידו.
- להכין עותק הדגמה נפרד של אותו פרויקט, עם ה-workflow המלא ממדריך הסטודנט. לא לבצע שינויי הדגמה בקובצי Part 2 המקוריים.
- לבדוק מחדש את action versions וה-runner. הטיוטה משתמשת ב-checkout v7.0.1 וב-setup-python v7.1.0. שם ה-Python הוא `"3.10"`; אין קשר בין גרסת ה-action לגרסת Python.
- ה-Dockerfile נקרא `dockerfile`. לבדוק שהפקודה משתמשת ב-`-f dockerfile` וב-context המתאים. `.dockerignore` מרשה את קובצי הבנייה הדרושים, ולא את סביבת הפיתוח המקומית.
- לאמת YAML ומבנה workflow. לאחר יצירת הקבצים, לבדוק תלות/pytest/build מ-checkout חדש, בלי להסתמך על קובץ מודל חיצוני לתיקייה או על virtual environment שמישהו העתיק לתוכה.
- להכין מראש הרצות הדגמה אמיתיות, אם אפשר, ולוודא את ה-commit המתאים לכל אחת. לא לתכנן המתנה להתקנות ארוכות בתוך שלוש דקות ההדגמה.
- לשמור את מסמכי החלופה זמינים מקומית. הסיכומים שלהם מסומנים כהמחשה בלבד; הם אינם הקלטה של GitHub ואינם ראיה שה-build כבר עבר.

## איך להכין את הדגמת הכישלון וההצלחה

להשתמש במאגר הדגמה שהמרצה יצר עבור הקורס. אלה הוראות הכנה, לא טענה שההרצות כבר בוצעו.

תחילה לבצע push לפרויקט התקין ולבדוק שהריצה כוללת `5 passed` ו-build שעבר. אחר כך לשנות **רק** את הציפייה ב-`test_health`:

```python
assert response.status_code == 201
```

לבצע commit ו-push רגילים בעותק ההדגמה:

```bash
git add test_api.py
git commit -m "Demo a failing health assertion"
git push
```

לפתוח את הריצה החדשה ולוודא בפועל: `test_health` נכשל בהשוואה בין 200 ל-201, הסיכום הוא `1 failed, 4 passed`, וה-build דולג. אין צורך להפעיל את המודל מחדש או לשנות את ה-API.

להחזיר את הציפייה ל-200, לבצע commit ו-push נוספים ולוודא ריצה תקינה:

```bash
git add test_api.py
git commit -m "Restore the correct health expectation"
git push
```

להשאיר פתוחות לשוניות של הריצה שנכשלה ושל הריצה המתוקנת. לבחור לפי הודעת commit והקוד של ההרצה, כדי לא להראות בטעות תוצאה ישנה שאינה קשורה לתיקון.

**הערה חשובה להדגמה:** Re-run של ההרצה הישנה בודק שוב את אותו commit. הוא אינו רואה תיקון שנשאר רק מקומית או שנמצא ב-commit חדש. לתוצאה המתוקנת מציגים את הריצה שנוצרה אחרי ה-push של התיקון.

אם ההדגמה לא בוצעה בפועל, לומר זאת ולעבוד עם הדוגמאות המסומנות. אין להציג את הסיכומים כאילו הועתקו ממאגר שכבר רץ.

## הסבר קצר על המושגים

- **Trigger:** אצלנו `push`, האירוע שמתחיל את ההרצה.
- **Workflow:** ההגדרה המלאה בשם `SMS API CI`.
- **Job:** קבוצת העבודה `check-and-build`, עם steps שרצים על אותו runner.
- **Runner:** המחשב שמבצע את ה-job. כאן GitHub מספק Ubuntu; מערכת ההפעלה של הסטודנט יכולה להישאר Windows או macOS.
- **Step:** משימה אחת. `uses` מפעיל action, ו-`run` מריץ פקודה. בדוגמה יש חמישה steps שהגדרנו, וייתכנו גם כניסות setup/cleanup אוטומטיות בתצוגת GitHub.

אם סטודנט מתבלבל בין job למחשב, להצביע על `check-and-build` לעומת `runs-on`. אין צורך להרחיב למספר jobs או להרצות מקבילות.

אין להוסיף `continue-on-error` או לשנות את הבדיקות כדי לעקוף כישלון. בנייה שממשיכה למרות בדיקות שנכשלו אינה תוצאת המעבדה שהגדרנו.

## ליווי התרגול

### הכנת המאגר

לוודא שהסטודנט עובד בתיקייה נפרדת עבור המאגר שלו ומעתיק אליה את קובצי השירות שהשלים, כולל `.gitignore` ו-`.dockerignore`. לא מעתיקים `.git` של מאגר הקורס או virtual environment.

להזכיר שהשמות `main.py`, `model.joblib`, `test_api.py` וקובצי requirements נמצאים בשורש המאגר החדש. הנתיב שממנו חילקנו את התרגול בחומרי הקורס אינו צריך להופיע בתוך ה-workflow של המאגר הקטן.

אם יש תקלה ב-Git identity או ב-sign-in, לעזור בהכנה הבסיסית ולהפעיל את חלופת הקריאה בזמן ההמתנה. אין צורך להסביר ניהול secrets של CI כדי לפתור חיבור רגיל של המשתמש למאגר.

### ה-workflow

לבדוק שהסטודנטים שומרים את הקובץ ב-`.github/workflows/ci.yml`, משלימים את ארבעת הערכים ושומרים spaces במקום tabs. בשלב זה הם צריכים להסביר מה `on`, `runs-on` ו-`run` עושים, לא לכתוב YAML מתקדם.

### הקבצים ב-commit

לבקש להראות את `git ls-files` ואת רשימת הקבצים ב-GitHub. אם המודל קיים רק מקומית, הוא לא יהיה זמין ל-runner. אם כלל ignore כללי מסתיר את המודל שסופק לכיתה, לזהות את הכלל ולתקן את ההסתרה של הארטיפקט הזה. לא להכניס אימון ל-CI כתחליף למסירת הקובץ.

### הלוגים

לבקש לזהות את ה-step שנכשל לפני שמציעים שינוי. שאלות מסייעות: ״ה-workflow התחיל בכלל?״, ״החבילות הותקנו?״, ״זו שגיאת import או assertion?״, ״ה-build רץ או דולג?״.

לא לפתור עבור הסטודנט את כל הקובץ מיד. להפנות לשורת השגיאה ולחלק המתאים במדריך. עדיין יש כאן הכוונה מפורטת; עצמאות רחבה תגיע באתגר של Part 5.

## טעויות נפוצות

- **מיקום workflow שגוי:** GitHub מחפש ב-`.github/workflows/` של שורש המאגר. קובץ שנשאר תחת נתיב הפצה מחומרי הקורס לא יימצא במקום המצופה.
- **גרסת Python ללא quotes:** לשמור `"3.10"` כמחרוזת, ולא להשאיר לכלי YAML לפרש אותה כמספר.
- **תלויות פיתוח חסרות:** אם מותקנות רק runtime requirements, pytest או HTTPX עלולים להיות חסרים. להשתמש ב-`requirements-dev.txt` שכבר הוגדר ב-Part 2.
- **המודל חסר בזמן import:** לבדוק commit, ignore ומיקום ליד `main.py`. הכישלון מתרחש לפני assertions; אין צורך לשנות ציפיית status כדי לפתור אותו.
- **הועתקה גרסת Part 2 לא גמורה:** TODO בקבוצת התוויות או היעדר `max_length=500` מסבירים כישלון של בדיקות קיימות. לשחזר את ההשלמה שנדרשה ב-Stage A, לא לשנות את מבחן ההצלחה.
- **Docker לא מוצא קובץ:** לבדוק שם קובץ באותיות קטנות, `-f dockerfile`, context `.` וקבצים מנוהלים שנכנסו ל-checkout. אין צורך לשנות את ה-Dockerfile כדי לחפש קובץ מחוץ לפרויקט.
- **build דולג:** אחרי pytest שנכשל זו ההתנהגות שתכננו. יש לפתור את הכישלון שקדם לו.
- **GitHub עדיין מציג ריצה ישנה:** לבדוק איזה commit נבדק. תיקון שלא בוצע לו push אינו נגיש ל-runner.
- **אין כפתור Run workflow:** הקובץ שלנו מפעיל `push` בלבד. אין `workflow_dispatch` ולא צריך להוסיף אותו כדי להשלים את המעבדה.
- **קושי ב-authentication:** הגישה הרגילה של הסטודנט ל-GitHub נפרדת מה-token האוטומטי שבו actions משתמשים. לא מכניסים סיסמה ל-YAML.

## תשובות לחלופת הקריאה

בטבלת הזיהוי: trigger הוא `push`; ה-job הוא `check-and-build`; ה-runner הוא `ubuntu-latest`; Python הוא `3.10`; הפקודות הן pytest ו-Docker build כפי שמופיעות בפתרון המלא. התקנת תלויות מתבצעת ב-`Install dependencies`.

בדוגמת הכישלון: `Run API tests` נכשל בפונקציה `test_health`; התקבל 200 והציפייה המכוונת הייתה 201. מחזירים את הציפייה ל-200, ואז מבצעים commit/push של התיקון. ה-build דולג מפני שהבדיקות נכשלו.

בדוגמת ההצלחה: הסיכום מתאר בדיקות שעברו ו-image שנבנה. הוא אינו מתאר אימון, פרסום, deployment או מדידת precision/recall. עצם קריאת דוגמה אינה מוכיחה שבוצעה הרצה אמיתית.

הרצה מקומית יכולה להראות שהבדיקות והבנייה עובדות במחשב המקומי. כדי להשלים את הראיה עבור GitHub Actions נדרש push אמיתי ובדיקה של תוצאות ההרצה ב-GitHub.

## משמעות התוצאה והסיום

הסטודנט צריך להראות `5 passed`, build שעבר ו-job מוצלח באותו commit. אין מספיק להראות רק צבע ירוק בלי לדעת אילו משימות הוגדרו.

ה-image נוצר על ה-runner. לא שומרים אותו כאן כתוצר הפצה, לא מפרסמים אותו ל-registry ולא מפעילים container כדי לבדוק בו חיזוי. גם ה-model quality לא נמדד מחדש. זהו סיום מוצלח של מעבדת CI בסיסית, ונקודת פתיחה לדיון בשחרור מבוקר ב-Part 4.

אפשר להזכיר במשפט שב-production יש עוד שיקולים של action versions, הרשאות, dependencies ו-secrets. לא פותחים עליהם משימות נוספות ולא מקדימים את פתרונות האתגר העצמאי.

**בדיקת איכות לפני הוראה:** YAML נבדק סטטית, ו-pytest ו-Docker build נבדקו מקומית בסביבה מבודדת. לא נצפתה הרצת GitHub אמיתית. להכין ריצות הדגמה מתארחות ולבדוק את הלוגים לפני השיעור; דוח QA מפריד בין סוגי הראיות.
