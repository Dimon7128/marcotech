## מטרת החלק

הסטודנטים צריכים להבין איך הופכים ציפייה מה-API לבדיקה שאפשר להריץ שוב. מסיימים עם שלוש בדיקות בסיסיות ועוד שתי בדיקות גבול: חמש פונקציות שעוברות ב-pytest. לא מלמדים כאן taxonomy של בדיקות, mocking, CI, או אימון מודל.

הבקשה להרחיב schema validation מיושמת בשני צעדים: קודם מסבירים ומוכיחים את הכללים שכבר קיימים, ואז מוסיפים כלל אורך אחד ובודקים אותו. חשוב לא להציג מספר, `null` או טקסט ריק כאילו הוספנו עכשיו את הדחייה שלהם; הם כבר נדחים ב-schema ההתחלתי.

**הכלל החדש בתרגול:** `max_length=500`, אחרי trimming. זהו גבול שאנחנו בוחרים לצורך ה-API של התרגול. אין לקשור אותו למגבלה אוניברסלית של SMS או לטענה שהמודל מסווג טוב יותר עד 500 תווים.

## איך להסביר schema בלי להסתבך

אפשר לומר: ״schema הוא תיאור של הטופס שהשירות מקבל. צריך שדה בשם `message`, הערך שלו צריך להיות טקסט, והטקסט צריך לעמוד בכללי האורך״.

להדגים בעל פה שלוש הבחנות:

- **מבנה לעומת סוג:** שדה חסר מפר דרישת חובה; מספר בתוך `message` מפר את סוג הערך. בשני המקרים ה-JSON עצמו יכול להיות תקין מבחינה תחבירית.
- **ניקוי לעומת בדיקה:** trimming מסיר רווחים מהקצוות; מינימום האורך בודק מה נשאר. הוא אינו מסיר את הרווחים בתוך המשפט.
- **כלל קיים לעומת דרישה חדשה:** חסר/ריק/רווחים/`null`/מספר כבר נדחים. מקסימום 500 הוא כלל חדש שנוסיף. לפני הוספתו, בדיקה שמצפה לדחיית 501 אמורה להיכשל.

לא להוסיף regex, חסימת קישורים, חסימת מילות spam, validators מותאמים או איסור על סימני פיסוק. אנחנו בודקים קלט מתאים לשירות, לא מנסים להחליף את המודל בכלל ידני לסיווג spam.

## הדגמה: assertion נכשל אינו בהכרח API שבור

להחזיר את הציפייה ל-200 ולהריץ שוב. לסיים בהצלחה ולוודא שהשינוי הזמני נשמר בחזרה. ההדגמה הזאת שונה מהדרישה החדשה של מקסימום אורך: שם נוסיף ציפייה מכוונת שמייצגת שינוי מוסכם במדיניות הקלט.

לא להריץ כרגע את כל ה-starter: בדיקת החיזוי עדיין כוללת TODO, ועלולה להסיט את הדיון לתקלה שאינה תקלה.

## פתרון למשימות

### השלמת קבוצת התוויות

```python
assert response.json()["label"] in {"spam", "ham"}
```

הבדיקה אינה אומרת שהסיווג נכון. היא אומרת שהשדה הנדרש מכיל ערך מותר. אין לקבע `ham` או `spam` למשפט הסינתטי ללא מטרה מפורשת של בדיקת התנהגות מודל ידועה.

### כלל האורך הסופי

```python
class SMSRequest(BaseModel):
    message: Annotated[str, StringConstraints(
        strip_whitespace=True, min_length=1, max_length=500
    )]
```

לא משנים את `message`, את `label`, את ה-routes או את קובץ המודל. זו הרחבה מפורשת של מדיניות הקלט בעותק המעבדה; אותו schema ימשיך גם ל-Part 3.

### קובץ הבדיקות הסופי למרצה

זהו פתרון ייחוס ל-Lab 1 המודרך. הסטודנטים מתחילים מהגרסה עם שלוש פונקציות ו-TODO, ומוסיפים את שני מקרי הגבול לפי המדריך.

```python
from fastapi.testclient import TestClient

from main import app

client = TestClient(app)


def test_health():
    response = client.get("/health")
    assert response.status_code == 200
    assert response.json() == {"status": "ok"}


def test_valid_prediction():
    response = client.post("/predict", json={"message": "Meeting at five"})
    assert response.status_code == 200
    assert "label" in response.json()
    assert response.json()["label"] in {"spam", "ham"}


def test_invalid_input():
    invalid_payloads = [
        {},
        {"message": ""},
        {"message": "   "},
        {"message": None},
        {"message": 123},
    ]
    for payload in invalid_payloads:
        response = client.post("/predict", json=payload)
        assert response.status_code == 422, payload


def test_maximum_length_is_accepted():
    response = client.post("/predict", json={"message": "x" * 500})
    assert response.status_code == 200
    assert response.json()["label"] in {"spam", "ham"}


def test_overlong_message_is_rejected():
    response = client.post("/predict", json={"message": "x" * 501})
    assert response.status_code == 422
```

## תקלות נפוצות והכוונה

- **שגיאה בזמן collection או import:** אם חסר `model.joblib`, פותרים קודם את מסירת המודל והסביבה. זה אינו כישלון של assertion. המודל צריך להיות ליד `main.py`, לא רק בתיקיית עבודה אחרת.
- **ייבוא של קובץ אחר:** לבדוק שה-terminal פתוח ב-`sms-service/` של Lab 1, שהקובץ נקרא `test_api.py` ושמשתמשים ב-`python -m pytest`. אין צורך לשנות `sys.path` כדי ללמד את המעבדה הזאת.
- **אין pytest או httpx:** להתקין את `requirements-dev.txt` באמצעות אותו Python שמריץ את הבדיקות. לא להתקין תלויות במערכת אחת ולבדוק דרך interpreter אחר.
- **PowerShell חוסם activation:** להשתמש ישירות ב-`.\.venv\Scripts\python.exe` עם אותן פקודות, כפי שמופיע במדריך. אין צורך לשנות מדיניות כללית של המחשב.
- **הסטודנט מצפה ל-200 על קלט לא תקין:** להסביר שהבדיקה בודקת האם ה-API דחה את הבקשה כנדרש. כאן 422 הוא תוצאה צפויה, ולכן הוא מוביל ל-Pass.
- **המשפט קיבל תווית אחרת מהניחוש:** לבדוק את ה-assertion. בבדיקת API מותרת כל אחת משתי התוויות. איכות מודל נבדקת בנפרד על נתונים מתויגים.
- **הודעת רווחים עוברת:** לוודא ש-`strip_whitespace=True` ו-`min_length=1` נשמרו, ושלא בודקים עותק אחר של האפליקציה.
- **501 תווים מתקבלים:** לפני הוספת הכלל זו ההתנהגות ההתחלתית הצפויה. אחרי ההוספה לבדוק שהקובץ נשמר ושיש `max_length=500`. אין שרת שצריך לעשות לו reload: כל הרצת pytest חדשה טוענת את הקוד השמור.
- **500 תווים נדחים:** לבדוק את הגבול ואת בניית המחרוזת. אין לשנות את הבדיקה לקבל 499 במקום לתקן מגבלה שגויה.
- **רוצים לבדוק את כל גוף שגיאת ה-validation:** אפשר להראות בהדגמה את `detail` ואת מיקום השדה, אבל לא להעמיס על התרגול assertion שתלוי בכל ניסוח השגיאה.
