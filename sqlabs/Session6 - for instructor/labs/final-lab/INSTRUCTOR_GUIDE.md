## A — מדיניות לשדות לא צפויים

**הסבר למרצה:** ברירת המחדל של המודל ההתחלתי מתעלמת משדות נוספים. זו אינה תקלה ב-Pydantic. הצוות מוסיף עכשיו דרישה מפורשת: בקשה עם שדה לא צפוי צריכה להידחות ב-422.

בדיקת ייחוס שאפשר להוסיף לחמש הבדיקות הקיימות:

```python
def test_unexpected_request_field_is_rejected():
    response = client.post(
        "/predict", json={"message": "Meeting at five", "unexpected": True}
    )
    assert response.status_code == 422
```

לפני שינוי המדיניות, הבדיקה החדשה צפויה להיכשל: הבקשה התקינה מבחינת `message` מתקבלת ב-200. בדיקות הבסיס ממשיכות לעבור. פתרון אפשרי הוא שינוי המודל ב-`main.py`:

```python
from pydantic import BaseModel, ConfigDict, StringConstraints


class SMSRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    message: Annotated[str, StringConstraints(
        strip_whitespace=True, min_length=1, max_length=500
    )]
```

`Annotated` כבר מיובא בקובץ. לשמר את כל יתר הקוד, הבדיקות והמודל. פתרון הייחוס המלא נמצא ב-`solutions/option_a_main.py` וב-`solutions/option_a_check.py`; הם אינם קובצי התחלה לסטודנטים. בהרצת הייחוס יש שש פונקציות: לפני התיקון `1 failed, 5 passed`, ואחריו `6 passed`. פתרון עם parametrization יכול להציג מספר מקרים אחר ועדיין להיות תקין.

**טעויות נפוצות:** שולחים הודעה ריקה יחד עם השדה הנוסף, ולכן מקבלים 422 גם בלי המדיניות החדשה; מוחקים את בדיקות הגבול; מכניסים את ההגדרה למחלקה אחרת; בודקים דווקא את נוסח הודעת השגיאה במקום את ההתנהגות הנדרשת.

**רמזים בהדרגה — למסור אחד בכל פעם:**

1. האם `message` שבבקשת הניסוי תקין בפני עצמו? מה קורה לשדה האחר כיום?
2. חפשו בתיעוד Pydantic את האפשרויות לשדות נוספים במודל קלט.
3. בדקו את אפשרות `extra` של `ConfigDict`, וחשבו איזו מדיניות מייצגת דחייה. הקפידו שהגדרות האורך וה-trimming יישארו.

**איך לעזור בלי לפתור:** לבקש להראות שתי בקשות שנבדלות רק בשדה הנוסף ואת התוצאות שלהן. אם הבדיקה עוברת לפני השינוי, לשאול איזו דרישה קיימת כבר גורמת לדחייה. לא להדביק מיד את מחלקת הייחוס.

## B — סוג התוכן של תגובת החיזוי

**הסבר למרצה:** `response.json()` מפענח את גוף התגובה; הוא אינו מוכיח שהכותרת מכריזה על JSON. רוצים check שמזהה שגיאה אמיתית בחוזה HTTP, בלי לקבע תווית חיזוי אחת להודעה שרירותית.

בדיקת ייחוס נוספת:

```python
def test_prediction_declares_json_media_type():
    response = client.post("/predict", json={"message": "Meeting at five"})
    assert response.status_code == 200
    assert "label" in response.json()
    assert response.json()["label"] in {"spam", "ham"}
    media_type = response.headers.get("content-type", "").split(";", 1)[0]
    assert media_type.strip().lower() == "application/json"
```

הפיצול מאפשר גם פרמטרים תקינים כגון `application/json; charset=utf-8`. שם הכותרת אינו תלוי באותיות גדולות/קטנות. אין לדרוש התאמה מחרוזתית נוקשה לכל הכותרת אם ההצהרה תקינה.

לצורך הוכחת זיהוי במאגר אימון בלבד, פתרון ייחוס שלילי יכול להחזיר גוף JSON עם Content-Type שגוי. להוסיף זמנית `from fastapi.responses import JSONResponse`, ולהחליף **רק** את ה-return של `predict`:

```python
return JSONResponse(
    content={"label": label}, headers={"Content-Type": "text/plain"}
)
```

במצב הזה הגוף עדיין מכיל label תקין, ולכן חמש בדיקות הבסיס עוברות והבדיקה החדשה נכשלת. לאחר החזרת `return {"label": label}` התוצאה הצפויה היא `6 passed`. מותר להשתמש בשינוי שלילי אחר אם הסטודנט מראה שהוא בודק בדיוק את הדרישה שנוספה. לא משאירים את התגובה השגויה בגרסה הסופית.

קובץ `solutions/option_b_check.py` מכיל את בדיקת הייחוס. אין צורך לשנות את המודל או את דרישות התלויות כדי להשלים מסלול זה.

**טעויות נפוצות:** מוסיפים רק קריאה נוספת ל-`.json()`; גורמים ל-500 ואז מייחסים את הכישלון לכותרת; בודקים `text/plain` כערך הרצוי; משאירים את השינוי השלילי אחרי ההדגמה; מקבעים `spam` להודעה אחת בלי הצדקה.

**רמזים בהדרגה:**

1. מה ההבדל בין גוף התגובה לבין מה שהשרת מצהיר על הגוף?
2. בדקו אילו נתונים נמצאים ב-`response.headers`, ואיזו כותרת מתארת את סוג התוכן.
3. בידקו את מדיית `application/json` בנפרד מפרמטרים שאחרי `;`. להוכחה, צריך מקרה שבו הגוף עדיין JSON אבל ההצהרה שגויה.

**איך לעזור בלי לפתור:** לבקש להציג status, body וכותרות של אותה תגובה, ולומר במילים מה התנאי החדש אמור לזהות. אם ניסוי שלילי מפיל גם את בדיקות הבסיס, לשאול איך לבודד את ההבדל בכותרת בלבד.

## C — CI גם ל-pull requests

**הסבר למרצה:** שינוי YAML לבדו אינו מספיק. הראיה המרכזית היא run אמיתי שהאירוע שלו הוא `pull_request`, עם הלוגים של אותו job. Push ל-feature branch כבר נבדק ב-Lab 1; הוא לא מוכיח את התוספת.

פתרון ייחוס מינימלי שומר על אותו job, אותן הרשאות ואותם steps ומשנה את האירועים ל:

```yaml
on: [push, pull_request]
```

אפשר גם מיפוי YAML תקין עם שני האירועים. קובץ ייחוס מלא נמצא ב-`solutions/option_c_ci.yml`, לשימוש במאגר הסטודנט ב-`.github/workflows/ci.yml`. אין צורך ב-`pull_request_target`, secrets, conditions מורכבים או job נוסף.

להפעיל את אותו workflow דרך פתיחת PR מתוך branch במאגר האימון האישי, ולזהות את סוג האירוע ואת ה-commit שנבדק. מאחר ששני האירועים פעילים, ייתכנו שתי הרצות עבור שינוי אחד; יש לבחור את הרצת ה-PR הנכונה. workflow של `pull_request` עשוי לבדוק commit מיזוג זמני; אין לבלבל בינו לבין ה-head של ה-branch.

לראיית חסימה, אפשר לשנות זמנית ב-branch האימון את ציפיית `test_health` מ-200 ל-201, כפי שהמרצה הדגים ב-Part 3. הרצת ה-PR צפויה להציג `1 failed, 4 passed`, עם Docker build שדולג. להחזיר ל-200 ולהראות שההרצה המעודכנת עוברת ושנבנה image. אין צורך לבצע merge או לשבור main משותף.

**טעויות נפוצות:** מצרפים רק push run; לא שומרים את ה-workflow לפני ה-commit; פותחים PR לתיקייה/מאגר הלא נכון; מציגים רק overall green בלי pytest/build logs; מוסיפים `continue-on-error` כדי להגיע לבנייה. אם PR נמצא במצב merge conflict, GitHub עשוי לא להריץ `pull_request`; להתייחס לחסימה הזאת ולא לשנות אירוע מסוכן יותר כדי לעקוף אותה.

**רמזים בהדרגה:**

1. איזה אירוע מפעיל את ה-workflow הנוכחי, ואיזה אירוע חסר בדרישה?
2. חפשו בתיעוד GitHub את אירועי `push` ו-`pull_request`. חשבו איך לשמור את הראשון ולהוסיף את השני.
3. הסתכלו על `on` ועל metadata של ה-run. אחרי השינוי, פתחו או עדכנו PR במאגר שלכם ובחרו את ההרצה שהאירוע שלה הוא `pull_request`.

**איך לעזור בלי לפתור:** לשאול מה כתוב בשדה האירוע של ההרצה שמוצגת. אם רואים שתי הרצות, לבקש להסביר למה. אם אין הרצה, לבדוק יחד repo, branch ו-commit לפני שמציעים שינוי בקוד.

## ראיות, הערכה וסיום

לא לדרוש פורמט ארוך. דוח `CHALLENGE_REPORT.md` צריך לזהות משימה, פער, הסבר קצר, ראיות זיהוי/כישלון והצלחה, commit או קישור ל-run, תוצאת pytest ותוצאת build סופיות, ומגבלות שעדיין לא נבדקו.

להעריך ארבעה דברים: השיפור תואם למשימה; הבדיקות המקוריות נשמרו; יש ראיה רלוונטית לדרישה החדשה; הגרסה הסופית עוברת ונבנית. ריצה ירוקה עקב דילוג על הבדיקות או שינוי assertion שרירותי אינה פתרון. אין להכשיל פתרון תקין בגלל מספר פונקציות שונה מזה של הייחוס.

ב-GitHub לא זמין: לשמר חקירה עצמאית עם pytest ו-Docker מקומיים, ככל שקיימים. לתעד את התוצאות האמיתיות ולסמן ראיה מתארחת כ-**NOT VERIFIED**. דוגמאות [חלופת הקריאה](../lab1/part3_offline_inspection.md) מיועדות לפענוח, ולא מוכיחות שהשיפור של הסטודנט עבר. במסלול C אפשר לבחון YAML ולהסביר את ההתנהגות הצפויה, אך השלמת הוכחת האירוע מחייבת PR אמיתי מאוחר יותר.
